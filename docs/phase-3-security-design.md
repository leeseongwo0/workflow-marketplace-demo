# Phase 3 security design

This document freezes the offline crypto, storage-integrity, and key-custody
boundaries before adapter and bootstrap plumbing.

## Canonical bytes and hashes

- Canonical JSON is the project-local deterministic format: UTF-8 JSON without
  whitespace, object keys sorted lexicographically, array order preserved, and
  non-JSON or non-finite values rejected.
- The public manifest hash is SHA-256 over canonical public-manifest bytes.
- The encrypted bundle hash recorded on Sui is SHA-256 over canonical encrypted
  envelope bytes exactly as uploaded to Walrus.
- Hashes are lowercase 64-character hexadecimal at string boundaries and
  32-byte arrays internally.
- Downloaded Walrus bytes are hashed and compared before JSON parsing or
  decryption.

## Bundle encryption

- Cipher: AES-256-GCM using Node's native crypto implementation.
- DEK: exactly 32 random bytes.
- Nonce: exactly 12 fresh random bytes for every encryption.
- Authentication tag: exactly 16 bytes.
- Plaintext: canonical JSON bytes of a strict `google_news_rss/v1` bundle.
- AAD: canonical UTF-8 bytes of exactly `domain`, `rootId`, `version`, and
  `publicManifestHash`, with domain `AIWF_BUNDLE_V1`.
- The envelope stores the exact AAD bytes as canonical base64. Decryption also
  receives independently expected AAD, compares the bytes, and then lets GCM
  authenticate them. The envelope cannot choose its own trusted AAD.
- `keyId` is `root:<normalized-root-id>:release:<version>` and must agree with
  the expected AAD.

## Key custody

- `KeyProvider` is server-only and returns byte arrays; the browser never imports
  or calls it.
- `LocalDemoKeyProvider` reads an ignored local keyring with strict schema
  `local-keyring/v1` and requires every DEK to decode to exactly 32 bytes.
- Release, license, and runner authorization happens before key retrieval in the
  executor. The local demo provider intentionally does not claim Seal policy
  enforcement or production-grade custody.
- Keyrings, DEKs, executor private keys, decrypted bundles, and full environment
  objects must never be logged or written to committed state.

## Receipt BCS

- TypeScript encodes the frozen Move `ReceiptMessage` layout directly: a BCS
  byte vector domain, three 32-byte addresses, three 32-byte BCS vectors, and a
  little-endian `u64` timestamp in declared field order.
- The domain is fixed to `AIWF_RECEIPT_V1`; callers cannot override it.
- A golden vector generated by the Phase 2 Move test must match byte-for-byte in
  TypeScript before executor integration.

## Walrus boundaries

- Publisher and aggregator origins are configuration and must use HTTPS outside
  deterministic tests.
- Upload accepts only the documented `newlyCreated.blobObject.blobId` and
  `alreadyCertified.blobId` response shapes.
- Reads use `/v1/blobs/<blob-id>`, an abort timeout, a maximum byte count, and
  bounded retry with injected sleep for deterministic tests.
- Immediate aggregator lag may be retried, but retry count and delay are finite.
- A successful HTTP response is not sufficient: retrieved bytes must exactly
  match both the uploaded bytes during bootstrap and the Sui-recorded SHA-256
  hash during execution.

## Phase boundary

Phase 3 does not verify wallet signatures or on-chain licenses and does not run
the workflow. Those sequencing rules remain Phase 4. Phase 3 does not implement
Seal, Nautilus, TEE, arbitrary code execution, or browser-side decryption.
